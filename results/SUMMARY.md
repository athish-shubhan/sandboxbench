Generated by `bench/plot.py` from `results/*.json`.

Host: Intel(R) Xeon(R) Processor @ 2.80GHz, 2 vCPU, 7.8 GiB, kernel 6.18.44-fc-v180, KVM not available. runc version 1.5.2; runsc built from gVisor's go branch at commit ace9117e (release-20251215.0-48), flags --platform=systrap --network=none. Both runtimes run the same OCI bundle: a read-only bind of the host root filesystem, tmpfs /tmp, /work bind-mounted from the host, no network namespace interfaces besides lo, Docker-like capabilities and a seccomp deny list.

## 5. Memory per idle sandbox

16 sandboxes running `sleep infinity` at once. PSS sums the proportional set size of every host process belonging to the sandboxes (the container process for runc; sentry, gofer and stub processes for runsc). MemAvailable drop also includes kernel memory, after dropping caches.

| runtime | host processes per sandbox | PSS per sandbox | MemAvailable drop per sandbox | idle sandboxes per 64 GiB (by PSS) |
|---|---|---|---|---|
| runc | 1 | 0.2 MiB | below noise (<1 MiB) | 348,052 |
| runsc | 5 | 13.3 MiB | 11.1 MiB | 4,922 |

runc is driven directly here, without containerd's per-pod shim process, so its row is only the container's own process. Idle density is an upper bound: a real agent sandbox holds a working set (an interpreter, a repo, test processes) far larger than either runtime's overhead.

## 7. Warm-pool policies (simulation)

Discrete-event simulation of 14 days of claims; policies are scored on days 8-14 and the predictive policy learns from days 1-7. Claims: interactive agent sessions (diurnal Poisson), a nightly eval suite of 600 tasks (launch time jittered +/-10 min, 100 concurrent), PR-triggered eval suites on weekdays (80-300 tasks, 100 concurrent), and an RL job that claims 128 sandboxes at once every step (10:00-22:00). Creating a sandbox takes a lognormal scheduling delay (median 2 s) plus a runsc claim-to-first-exec sample from section 1, with at most 32 creations in flight. A claim served from the warm pool takes 50 ms. SLO: 1 s. Hints: the eval scheduler announces each suite and the RL trainer announces its next step when training starts (both up to 90 s ahead); the policy acts on them 30 s ahead.
